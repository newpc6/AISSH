# AI SSH 开发计划文档

## 1. 文档目的

本文档用于定义 AI SSH 的开发执行计划、里程碑拆分、交付物、工程规则和更新流程。

它必须始终与项目实际进度保持同步。任何较大的范围、架构、优先级或交付顺序变化，都需要体现在本文档中。

## 2. 工作约定

项目执行规则：

1. 每次里程碑调整或范围调整，都要更新本文档。
2. 如果调整同时影响产品设计或架构方向，需要同步更新 `docs/product-design.md`。
3. 每完成一批明确改动，都要进行一次清晰的 git 提交。
4. 不允许实现长期跑在文档前面，计划与实际要尽量同步。

## 3. 交付策略

整体按阶段推进：

1. 先证明桌面壳与 SSH 核心架构方向是可行的
2. 再交付真正可用的 SSH + 文件传输 MVP
3. 在 SSH 核心体验稳定后叠加 AI 能力
4. 最后做稳定性、打磨和发布准备

## 4. 里程碑

## Milestone 0：项目启动与骨架搭建

目标：

- 建立仓库结构、工程脚手架、编码规范和架构基线

交付物：

- 基础目录结构
- 前端工程初始化
- Go core 服务初始化
- 桌面壳方案设计落地
- 基础 IPC / API 契约
- lint / format / test 基础命令
- CI 基线
- 产品设计与开发计划文档

建议目录结构：

- `apps/desktop`
- `apps/core-go`
- `packages/shared-contracts`
- `docs/`

当前阶段说明：

- 文档基线已完成
- 当前已形成“前端 + Tauri 桌面壳 + Go core”的基础三层骨架
- 下一步进入 SSH 会话管理与终端容器开发

退出标准：

- 前端项目可运行
- Go core 可运行
- 前端可以通过最小接口拿到 core 的健康检查结果
- 目录结构、基础脚本、文档都已提交

## Milestone 1：SSH 核心连接能力

目标：

- 交付稳定的 SSH 连接与终端流能力

交付物：

- Host 数据模型与本地持久化
- 密码 / 私钥 / agent 认证支持
- known_hosts 校验流程
- 终端标签管理
- xterm.js 集成
- SSH 会话打开 / 关闭 / 重连
- 基础命令历史

退出标准：

- 用户可以保存主机并打开交互式 shell
- 终端足够稳定，可支撑日常命令执行
- 断开、重连状态清晰可控

目标：

交付物：

- 上传 / 下载

- 传输进度展示
- 失败重试与错误反馈
- 基础文件操作

退出标准：

- 用户可以稳定浏览远程文件并进行上传下载
- 常见传输失败有清晰反馈并可恢复

## 6. 工程规则

### 架构规则

- SSH / SFTP 逻辑放在 Go core，不直接放在前端
- 前端与 core 的通信契约必须显式定义、可演进
- AI provider 逻辑不要直接耦合进终端 UI 组件

### 产品规则

- AI 建议必须经过用户审核后才可执行
- host key 校验不能被静默跳过
- 敏感凭据优先使用操作系统安全存储

### 文档规则

- 范围、优先级、阶段变化必须同步更新本文档
- 若架构假设变化，需要同步更新产品设计文档
- 每次提交前检查文档是否仍和实现一致

## 9. 风险与应对

### 风险：本机代理或依赖环境影响 Rust 生态拉包

应对：

- 在仓库中保留 Cargo 配置
- 明确记录代理与依赖拉取问题
- 保持前端、桌面壳、Go core 三层可独立验证

### 风险：AI 功能喧宾夺主

应对：

- 在 SSH 与文件管理体验可用前，不提前推进大量 AI 功能

### 风险：安全债务积累

应对：

- 将密钥管理、host 校验、命令风险控制前置到 MVP

### 风险：界面打磨拖慢核心能力

应对：

- 先保证主流程可用，再逐步做高质量打磨

## 10. 文档变更规则

当实现方向发生变化时：

1. 先更新本文档，或与实现一起更新
2. 如果架构假设变化，同时更新 `docs/product-design.md`
3. 文档变更与相关代码一并提交
4. 保持里程碑状态准确
